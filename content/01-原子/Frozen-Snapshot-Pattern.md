# Frozen Snapshot Pattern（冻结快照模式）

> 会话开始时从磁盘加载一次状态并冻结为内存快照，会话期间的写入进入磁盘但不影响冻结的副本，确保会话内状态一致性。

---

## 一句话定义

**Frozen Snapshot Pattern = 启动时加载 → 冻结快照 → 读快照 + 写磁盘 → 下次启动重新加载**，用空间换一致性。

---

## 核心机制

```
会话开始
    ↓
load_from_disk()          ← 读一次，快照冻结在内存
    ↓
会话进行中...
  ├── 读：从冻结的内存副本读（一致性保证）
  └── 写：写磁盘 + 可选写内存（但不影响"基准版本"）
    ↓
会话结束 / 下次启动
    ↓
load_from_disk()          ← 再次读，拿到上次写入的最新版本
```

---

## 为什么要冻结？

**防止会话中途外部修改影响当前会话的一致性。**

场景举例：

| 外部事件 | 不冻结的后果 | 冻结后的行为 |
|---------|------------|------------|
| 另一个进程修改了文件 | 当前会话读到不一致的数据 | 继续用启动时的版本 |
| git checkout 切了分支 | 配置/记忆突然变化 | 不受影响，会话结束后才生效 |
| 手动编辑了配置文件 | 行为中途改变 | 保持启动时的状态 |

**你启动时看到什么，整个会话就看到什么。**

## 与 Prompt Cache 的关系

当冻结的快照内容被注入到 LLM API 调用时，**注入位置决定 cache 命中率**。

### Prompt cache 的工作原理

Prompt cache **从 prompt 开头匹配前缀**，前缀相同则命中缓存。

### 注入位置的影响

| 注入位置 | Cache 影响 |
|---------|-----------|
| System prompt 开头 | 每次内容不同 → **整个 cache 失效** |
| System prompt 末尾 | 前面稳定的部分命中 cache，只有尾部 miss |
| User message 尾部 | 历史对话的 cache 保留，只新消息不命中 |

### 最佳实践

把易变内容放在 prompt **末尾**，稳定内容放前面：

```
[稳定的系统指令]     ← cache 命中 ✅
[历史对话...]        ← cache 命中 ✅  
[临时注入：记忆/插件] ← 每次都不同，放最后，cache miss 只影响这一小段
[当前用户消息]       ← 不缓存
```

### 临时内容注入的正确做法

临时内容（记忆预取、插件上下文）在 API 调用时注入到用户消息的**副本**中，**从不进入存储的历史**：

```
存储的历史（干净）：
  User: "今天天气怎么样？"
  Assistant: "北京今天晴，25°C"

API 调用时（注入临时内容到副本）：
  System: [记忆预取] 用户喜欢简洁回答
  System: [插件上下文] 当前时间 2026-06-29
  User: "今天天气怎么样？"  ← 这是副本，带了额外上下文
  → 发给 LLM API
  → LLM 返回回答
  → 只把 User 和 Assistant 存入历史，临时内容丢弃
```

**为什么这样做**：
- 历史不被污染（下次加载不会重复塞记忆）
- 临时内容可以随时换（不同场景注入不同上下文）
- 节省存储（不用把每次都相同的系统提示存 N 遍）

## 真实案例

### 案例 1：Claude Code 的记忆系统

```
启动 Claude Code 会话
    ↓
load_from_disk()：读取 MEMORY.md + 项目记忆文件
    ↓
会话进行中：
  - 读记忆：从内存快照读（一致性）
  - 写记忆：写磁盘 + 更新内存
  - 但快照的"基准版本"不变
    ↓
下次启动：重新 load_from_disk()，拿到最新
```

### 案例 2：游戏存档系统

```
开始游戏
    ↓
加载存档到内存（冻结快照）
    ↓
游戏中：
  - 读取：从内存读（快速、一致）
  - 自动保存：写磁盘（但不影响当前内存状态）
  - 手动保存：写磁盘 + 可选重新加载
    ↓
退出 → 重新加载：拿到最新存档
```

### 案例 3：数据库事务

```
事务开始
    ↓
读取数据（快照隔离级别）
    ↓
事务进行中：
  - 读：始终读事务开始时的版本（MVCC）
  - 写：写 write-ahead log，但不影响快照
    ↓
事务提交：写入生效
    ↓
下一个事务：看到新版本
```

## 优缺点

### 优点

- ✅ **一致性**：会话内状态稳定，不受外部干扰
- ✅ **可预测**：启动时看到什么，整个会话就看到什么
- ✅ **隔离性**：多个会话互不影响
- ✅ **简化逻辑**：不用处理"中途状态变化"的边界情况

### 缺点

- ❌ **延迟更新**：外部修改要等下次启动才生效
- ❌ **内存占用**：需要同时维护快照和最新状态
- ❌ **版本冲突**：会话结束写回时可能覆盖别人的修改（需要 merge 策略）

## 变体

### 变体 1：Write-Through（穿透写）

写入时同时更新磁盘和内存快照：

```
写操作：
  1. 写磁盘
  2. 更新内存快照（但不影响"基准版本"的语义）
```

**适用**：需要会话内看到自己写入的内容。

### 变体 2：Write-Behind（延迟写）

写入先缓存在内存，定期批量写磁盘：

```
写操作：
  1. 写内存缓冲
  2. 后台线程定期 flush 到磁盘
```

**适用**：写操作频繁，需要性能优化。

### 变体 3：Copy-on-Write（写时复制）

读取时共享快照，写入时复制一份：

```
读操作：直接读快照（零拷贝）
写操作：复制快照 → 修改副本 → 下次启动用副本
```

**适用**：读多写少，需要节省内存。

## 相关模式

- [[01-原子/MVCC|MVCC]]（多版本并发控制）：数据库的快照隔离实现
- [[01-原子/Event-Sourcing|Event Sourcing]]：不存快照，只存事件，随时重建任意时刻的状态
- [[01-原子/CQRS|CQRS]]：读写分离，写端和读端用不同的模型

## 演化位置

```
传统文件读写（每次都读磁盘）
    ↓
内存缓存（读内存，写磁盘）
    ↓
Frozen Snapshot（会话级冻结，保证一致性）← **你在这里**
    ↓
MVCC（数据库级多版本并发）
    ↓
Event Sourcing（事件溯源，可回溯任意时刻）
```
